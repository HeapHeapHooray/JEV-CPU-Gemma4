Abstract. Semantic-if decisions — route this, is this a policy violation, what severity is this incident — are usually answered by having a chat model generate text that software then parses back into a branch. SemIf (an open reproduction of TypeSafe's Jev pattern) instead reads a decision directly from a model's option logits in a single forward pass, with no text generated. SemIf targets a GPU holding a 4B model. This report describes JEV-CPU, a small adaptation that runs the same engine on a commodity CPU with a 0.6B open model, and reports measurements from an 8 GB, GPU-less machine: qualitative decisions across eight domains, a latency-versus-input-length curve, and the resulting practical input ceiling. We make no claim of methodological novelty — the contribution is engineering and empirical: showing the method is device-agnostic, quantifying where CPU latency (not memory or the model) becomes the limit, and documenting how accuracy scales with model size.

1. Introduction

Most decisions inside software agents are small and typed: choose a queue, pick a severity, decide whether evidence supports a claim. A chat model can answer them, but generating an answer sentence and parsing it back into an if is slow and brittle. A decision-native alternative is to present the options as tokens and read the model's probability over exactly those tokens in one forward pass. TypeSafe's closed Jev service popularized this interface; SemIf reproduces the interface pattern with open models on a GPU.

This report asks a narrow, practical question: does the method still work with no GPU and a tiny model, and where does it break down?

2. Background

Reading a categorical decision from an LM's next-token distribution — rather than sampling text — is a well-established idea (verbalizer-style zero-shot classification, answer-token scoring, NLI cross-encoders). We claim no novelty for the mechanism. JEV-CPU is a CPU adaptation and empirical study of SemIf, which is itself an independent reproduction of the Jev pattern; Jev and TypeSafe are the property of their owners and are not affiliated with this work.

3. Method: reading a decision from logits

A decision is one record: a state (evidence), a question (criterion), and 2–16 typed options. The direct scoring path (unchanged from SemIf) is:

  1. Letter-choice prompt. Each option is labeled A, B, C… ; the system turn asks for a single uppercase letter, so the next token is the answer.
  2. Single-token pinning. Each letter is verified to encode to one round-tripping token that does not perturb tokenization — one clean vocabulary slot per option.
  3. One forward pass. The prompt runs once; we keep the final-position logits. No sampling, no decode loop, no JSON to repair.
  4. Softmax over slots. We gather only the option letters' token ids and softmax over those, giving a probability per option conditional on the declared set.

Latency is dominated by prompt prefill, not generation length — the property JEV-CPU relies on to stay usable on a CPU. Full code is in Appendix A.

4. System: the CPU port

SemIf forces a GPU in exactly one place — its loader checks for a single CUDA device and loads with device_map={"":"cuda:0"}, bfloat16. Everything downstream is device-agnostic: the scoring code follows device = next(model.parameters()).device and the only CUDA-specific call, torch.cuda.synchronize(), is guarded by if device.type == "cuda" (a no-op on CPU). JEV-CPU therefore changes only the loader (CPU / float32) and reuses SemIf's original scoring. A standard-library web server exposes it with a three-pane UI.

6. Latency and input-length limits

Two numbers are often conflated. The model's context window is 40,960 tokens — large even at 0.6B. SemIf's engine caps a decision at 4,096 tokens by default (a guard; configurable). Neither is the real constraint on CPU. Measured on the 8 GB CPU box, one decision with growing input:

Practical input ceiling. We treat ≈7,700 tokens (~117 s) as the usable maximum on this CPU: beyond it one decision crosses ~120 s, no longer useful, so larger inputs are considered unsupported here. Interactive ~1 s decisions want short states (≲~300 tokens).

7.1 Outlook — GPU serving and a production JEV

Accuracy (§7) and CPU latency (§6) are usually assumed to trade off, but a GPU relaxes both at once:

  • Latency collapses. Prefill is what GPUs are built for. SemIf reports a 4B model on one RTX 3090 returning 21 binary decisions in a median 1.02 s (vs 5.3 s to generate the equivalent JSON) — the same readout, just not latency-bound.
  • Input size grows. With the wall gone, practical input rises from ~7,700 tokens / ~120 s toward the model's full 40,960-token context — long documents, transcripts, code diffs in one pass.
  • Throughput multiplies. A decision is one forward pass, so decisions batch; shared-state prefix reuse amortizes a long state across criteria. SemIf measures ~20 decisions/s on one 3090.

Together, a larger open-weight model (4B+) on a GPU is simultaneously more accurate, accepts far larger inputs, and answers many decisions per second — with typed, auditable outputs and nothing to parse. That is the shape of a production, potentially commercial, JEV: semantic-if as a low-latency, high-throughput hosted service. JEV-CPU is the floor (portable to any machine); a GPU-served larger model is the ceiling that turns the same engine into a product.

Scope. We did not run GPU experiments here. The GPU latency/throughput figures are SemIf's published single-GPU (RTX 3090, 4B) measurements plus projections from our CPU curve (§6) — an implication, not our own results. Quantifying a GPU-served JEV (tokens/s, decisions/s, cost, concurrency) is the natural next study.

8. Limitations

  • No new method. The logit-readout mechanism is prior art; this is a port and measurement.
  • Small-model errors. At 0.6B secondary decisions can be inconsistent (the loan case flags high risk yet leans approve); larger models resolve this (§7).
  • Not a benchmark. §5 shows single runs; quantitative accuracy lives in SemIf's repo (cited in §7).
  • Single-machine measurements. Latencies are from one 8 GB CPU box and vary with hardware.
  • Probabilities are conditional on the declared options and uncalibrated as confidence.

9. Conclusion

Decision-native, logit-readout inference is not tied to a GPU or a large model. With only a loader change, SemIf's engine runs on a commodity CPU with a 0.6B model, decides across many domains at ~1 s each, and stays memory-stable well past its default token cap. On this hardware the honest limit is latency: inputs above ~7,700 tokens cross the ~120 s mark, and small-model accuracy — not context or memory — is what improves by scaling up. JEV-CPU is the reproducible floor; the same engine, given a larger open-weight model on a GPU, points toward the ceiling (§7.1) — an accurate, high-throughput, low-latency semantic-if service, i.e. a production JEV.

Appendix A. Code-level walkthrough: turning an open-weight model into a decision engine

A "JEV" / decision engine is not a fine-tune and not new weights — it is a way of calling an ordinary open-weight causal LM so a typed decision falls out of a single forward pass. The scoring code is SemIf's, reproduced verbatim; JEV-CPU changes only the loader (A.7). Snippets from src/semif_phase1/{core,direct}.py.

A.1 — The record and its validation

def validate_row(row):
    required = {"id", "state", "question", "options"}
    if not required <= row.keys(): raise ValueError(...)
    json.dumps(state, ensure_ascii=False, allow_nan=False)   # finite JSON
    if not isinstance(options, list) or not 2 <= len(options) <= len(LETTERS): raise ValueError(...)

A.2 — Building a letter-choice prompt

LETTERS = "ABCDEFGHIJKLMNOP"
DIRECT_SYSTEM = ("Apply the supplied criterion to the supplied evidence. "
                 "Choose exactly one listed option. Respond with only its "
                 "uppercase letter, with no explanation or reasoning.")

def direct_messages(row):
    payload = {"evidence": row["state"], "criterion": row["question"],
               "options": [{"letter": LETTERS[i], "description": o["description"]}
                           for i, o in enumerate(row["options"])]}
    return [{"role":"system","content":DIRECT_SYSTEM},
            {"role":"user","content":json.dumps(payload, ensure_ascii=False)}]

A.3 — Pinning each option to exactly one token

def _slot_ids(tokenizer, count):
    result = []
    for letter in LETTERS[:count]:
        encoded = tokenizer.encode(letter, add_special_tokens=False)
        if len(encoded) != 1 or tokenizer.decode(encoded) != letter:
            raise ValueError(f"Answer slot {letter!r} is not one exact round-trip token")
        result.append(encoded[0])
    if len(result) != len(set(result)): raise ValueError("Answer-slot tokens collide")
    return result            # token ids for A, B, C, ...

A.4 — Encoding and verifying the answer boundary

def encode_prompt(tokenizer, row, max_tokens):
    prompt = tokenizer.apply_chat_template(direct_messages(row), tokenize=False,
        add_generation_prompt=True, enable_thinking=False)
    ids = tokenizer.encode(prompt, add_special_tokens=False)
    if not ids or len(ids) > max_tokens: raise ValueError("exceeds limit; no truncation")
    slots = _slot_ids(tokenizer, len(row["options"]))
    for letter, token in zip(LETTERS, slots):
        if tokenizer.encode(prompt + letter, add_special_tokens=False) != ids + [token]:
            raise ValueError(f"Answer boundary changes tokenization for slot {letter}")
    return ids, slots, digest(prompt)   # sha256 for auditability

A.5 — One forward pass, last-position logits

def _forward(model, inputs):
    params = inspect.signature(model.forward).parameters
    kwargs = dict(inputs, use_cache=False, return_dict=True)
    if "logits_to_keep" in params: kwargs["logits_to_keep"] = 1
    return model(**kwargs).logits[:, -1, :]     # (batch, vocab); no sampling

A.6 — Gather the slots, softmax, decide

def score(model, tokenizer, row, metadata, max_tokens=4096):
    import torch
    ids, slots, prompt_hash = encode_prompt(tokenizer, row, max_tokens)
    device = next(model.parameters()).device          # follow the model
    inputs = {"input_ids": torch.tensor([ids], device=device),
              "attention_mask": torch.ones((1, len(ids)), device=device)}
    if device.type == "cuda": torch.cuda.synchronize(device)   # no-op on CPU
    with torch.inference_mode():
        vocabulary = _forward(model, inputs)[0].float()        # (vocab,)
    selected = vocabulary[slots].cpu().tolist()   # logits at A, B, C, ...
    return {"option_ids":[o["id"] for o in row["options"]],
            "option_logits": selected, "probabilities": softmax(selected), ...}

That is the entire "JEV-ification": a stock AutoModelForCausalLM is never asked to generate; it is asked once for its next-token logits, and the decision is the arg-max over the option slots.

A.8 — Reusing one state across many criteria (shared mode)

shared.py prefills the state once into a KV cache, replicates it with cache.reorder_cache(...), and evaluates every criterion's answer position in one batched forward via a vector logits_to_keep — one prefill, many decisions; also CUDA-synced only under CUDA.

1. 서론

소프트웨어 에이전트의 결정 대부분은 작고 타입이 정해져 있습니다: 큐 선택, 심각도 선택, 증거가 주장을 뒷받침하는지 판단 등. 챗 모델도 답할 수 있지만, 답 문장을 생성해 다시 if로 파싱하는 것은 느리고 취약합니다. 결정-네이티브 대안은 옵션을 토큰으로 제시하고, 바로 그 토큰들에 대한 모델의 확률을 한 번의 forward로 읽는 것입니다. TypeSafe의 비공개 Jev 서비스가 이 인터페이스를 알렸고, SemIf가 오픈 모델로 이 패턴을 GPU에서 재현했습니다.

본 리포트는 좁고 실용적인 질문을 던집니다: GPU 없이, 아주 작은 모델로도 이 방법이 동작하는가, 그리고 어디서 무너지는가?

2. 배경

텍스트를 샘플링하는 대신 LM의 다음-토큰 분포에서 범주형 결정을 읽는 것은 잘 확립된 아이디어입니다 (verbalizer 기반 zero-shot 분류, 답-토큰 스코어링, NLI 크로스-인코더 등). 이 메커니즘에 신규성은 주장하지 않습니다. JEV-CPU는 SemIf의 CPU 적응 및 실증 연구이며, SemIf 자체가 Jev 패턴의 독립적 재현입니다. Jev·TypeSafe는 각 소유자의 자산이며 본 작업과 무관합니다.

3. 방법: 로짓에서 결정 읽기

하나의 결정은 하나의 레코드입니다: state(증거), question(기준), 2–16개의 타입드 options. direct 스코어링 경로(SemIf 그대로)는:

  1. 레터-초이스 프롬프트. 각 옵션에 A, B, C…를 부여; 시스템 턴이 "대문자 한 글자만" 답하게 하여 다음 토큰이 곧 답이 됩니다.
  2. 단일 토큰 고정. 각 레터가 토큰화를 흔들지 않고 정확히 1토큰으로 round-trip됨을 검증 — 옵션마다 깨끗한 어휘 슬롯 하나.
  3. 1회 forward. 프롬프트를 한 번 실행하고 마지막 위치의 로짓만 취합니다. 샘플링·디코딩 루프· JSON 복구 없음.
  4. 슬롯에 대한 softmax. 옵션 레터 토큰만 모아 softmax하여, 선언된 옵션 집합에 조건부인 옵션별 확률을 얻습니다.

지연은 생성 길이가 아니라 프롬프트 prefill이 지배하며, 이것이 JEV-CPU가 CPU에서 쓸 만한 이유입니다. 전체 코드는 부록 A 참조.

4. 시스템: CPU 포트

SemIf가 GPU를 강제하는 곳은 정확히 한 군데 — 로더가 단일 CUDA 디바이스를 확인하고 device_map={"":"cuda:0"}, bfloat16으로 로드합니다. 그 이후는 모두 디바이스 독립적입니다: 스코어링 코드는 device = next(model.parameters()).device를 따르고, 유일한 CUDA 전용 호출인 torch.cuda.synchronize()는 if device.type == "cuda"로 가드됩니다(CPU에선 no-op). 따라서 JEV-CPU는 로더만(CPU / float32) 바꾸고 SemIf의 원본 스코어링을 그대로 씁니다. 표준 라이브러리 웹 서버가 3분할 UI로 이를 노출합니다.

6. 지연과 입력 길이 한계

두 수치가 자주 혼동됩니다. 모델 컨텍스트 창은 40,960 토큰 — 0.6B여도 큽니다. SemIf 엔진은 결정당 기본 4,096 토큰 상한을 둡니다(가드; 조정 가능). CPU에서는 둘 다 실제 제약이 아닙니다. 8 GB CPU 박스에서 입력을 키우며 측정한 단일 결정:

7,697 토큰에서도 RAM은 ~3.5 GB로 평평하고 OOM이 없었습니다 — 여기서 한계는 메모리·모델이 아니라 prefill 지연(대략 제곱)입니다.

실용 입력 상한. 이 CPU에서 사용 가능한 최대치를 ≈7,700 토큰(~117 초)으로 둡니다: 이보다 크면 결정 하나가 ~120 초를 넘어 더 이상 유용하지 않으므로, 더 큰 입력은 여기서 미지원으로 간주합니다. 대화형 ~1 초 결정은 짧은 state(≲~300 토큰)를 필요로 합니다.

7.1 전망 — GPU 서빙과 상용 JEV

정확도(§7)와 CPU 지연(§6)은 보통 상충 관계로 여겨지지만, GPU는 둘 다 동시에 완화합니다:

  • 지연 붕괴. prefill은 GPU가 가장 잘하는 작업입니다. SemIf는 단일 RTX 3090에서 4B 모델이 21개 이진 결정을 중앙값 1.02 초에 반환한다고 보고합니다(동일 JSON 생성은 5.3 초) — 같은 판독인데 지연에 묶이지 않을 뿐입니다.
  • 입력 크기 증가. 벽이 사라지면 실용 입력이 ~7,700 토큰/~120 초에서 모델의 전체 40,960 토큰 컨텍스트로 올라갑니다 — 긴 문서·트랜스크립트·코드 diff를 한 번에.
  • 처리량 배가. 결정이 1회 forward라 배칭이 쉽고, shared-state 프리픽스 재사용이 긴 state를 여러 기준에 걸쳐 분할상환합니다. SemIf는 단일 3090에서 ~20 decisions/s를 측정합니다.

종합하면, GPU에서 서빙되는 더 큰 오픈웨이트 모델(4B+)은 동시에 더 정확하고, 훨씬 큰 입력을 받으며, 초당 많은 결정을 처리합니다 — 타입드·감사 가능 출력에 파싱도 필요 없이. 이것이 상용(잠재적 상업) JEV의 형태입니다: 저지연·고처리량의 호스팅형 semantic-if 서비스. JEV-CPU는 바닥 (어느 머신에도 이식 가능)이고, GPU로 서빙되는 더 큰 모델은 천장으로 같은 엔진을 제품으로 만듭니다.

범위. 본 리포트에서 GPU 실험을 수행하지는 않았습니다. 위 GPU 지연·처리량 수치는 SemIf의 공개 단일-GPU(RTX 3090, 4B) 측정과 우리 CPU 곡선(§6)으로부터의 추정이며, 우리 자신의 결과가 아니라 시사점입니다. GPU 서빙 JEV의 정량화(tokens/s, decisions/s, 비용, 동시성)가 자연스러운 다음 연구입니다.

8. 한계

  • 새 방법 아님. 로짓 판독 메커니즘은 선행 기술이며, 본 작업은 포트와 측정입니다.
  • 소형 모델 오류. 0.6B에서는 2차 결정이 비일관적일 수 있습니다(대출 사례는 high risk를 맞히면서도 approve로 기움); 더 큰 모델이 이를 해소합니다(§7).
  • 벤치마크 아님. §5는 단일 실행 예시이며, 정량 정확도는 SemIf 저장소(§7에서 인용)에 있습니다.
  • 단일 머신 측정. 지연은 하나의 8 GB CPU 박스 값이며 하드웨어에 따라 달라집니다.
  • 확률은 조건부이며(선언된 옵션에 대해) 신뢰도로서는 미보정입니다.

9. 결론

결정-네이티브 로짓 판독 추론은 GPU나 큰 모델에 묶이지 않습니다. 로더 변경만으로 SemIf 엔진은 0.6B 모델로 일반 CPU에서 돌아가고, 여러 도메인을 결정당 ~1초에 처리하며, 기본 토큰 상한을 훨씬 넘어서도 메모리가 안정적입니다. 이 하드웨어에서 정직한 한계는 지연입니다: ~7,700 토큰을 넘는 입력은 ~120초 선을 넘고, 개선되는 것은 컨텍스트나 메모리가 아니라 소형 모델의 정확도입니다. JEV-CPU는 재현 가능한 바닥이고, 같은 엔진에 GPU 위의 더 큰 오픈웨이트 모델을 주면 천장(§7.1) — 정확하고 고처리량·저지연인 semantic-if 서비스, 즉 상용 JEV — 을 가리킵니다.

부록 A. 코드 레벨 상세: 오픈웨이트 모델을 결정 엔진으로 만들기

"JEV"/결정 엔진은 파인튜닝도 새 가중치도 아닙니다 — 평범한 오픈웨이트 causal LM을 호출하는 방식으로, 타입드 결정이 단 한 번의 forward에서 나오게 하는 것입니다. 스코어링 코드는 SemIf의 것을 그대로 실었으며, JEV-CPU는 로더만 바꿉니다 (A.7). 스니펫 출처: src/semif_phase1/{core,direct}.py. (코드 주석은 원문 유지)

A.1 — 레코드와 검증

def validate_row(row):

A.2 — 레터-초이스 프롬프트 구성

LETTERS = "ABCDEFGHIJKLMNOP"
DIRECT_SYSTEM = ("Apply the supplied criterion to the supplied evidence. "
                 "Choose exactly one listed option. Respond with only its "
                 "uppercase letter, with no explanation or reasoning.")

def direct_messages(row):
    payload = {"evidence": row["state"], "criterion": row["question"],
               "options": [{"letter": LETTERS[i], "description": o["description"]}
                           for i, o in enumerate(row["options"])]}
    return [{"role":"system","content":DIRECT_SYSTEM},
            {"role":"user","content":json.dumps(payload, ensure_ascii=False)}]

시스템 턴이 "대문자 한 글자만" 답하게 하여, 생성될 다음 토큰 자체가 결정이 됩니다.

A.3 — 각 옵션을 정확히 1토큰으로 고정

def _slot_ids(tokenizer, count):
    result = []
    for letter in LETTERS[:count]:
        encoded = tokenizer.encode(letter, add_special_tokens=False)
        if len(encoded) != 1 or tokenizer.decode(encoded) != letter:
            raise ValueError(f"Answer slot {letter!r} is not one exact round-trip token")
        result.append(encoded[0])
    if len(result) != len(set(result)): raise ValueError("Answer-slot tokens collide")
    return result

각 레터가 정확히 1토큰으로 round-trip되고 서로 충돌하지 않아야, 로짓 비교가 깨끗해집니다.

A.4 — 인코딩과 답 경계 검증

def encode_prompt(tokenizer, row, max_tokens):
    prompt = tokenizer.apply_chat_template(direct_messages(row), tokenize=False,
        add_generation_prompt=True, enable_thinking=False)
    ids = tokenizer.encode(prompt, add_special_tokens=False)
    if not ids or len(ids) > max_tokens: raise ValueError("exceeds limit; no truncation")
    slots = _slot_ids(tokenizer, len(row["options"]))
    for letter, token in zip(LETTERS, slots):
        if tokenizer.encode(prompt + letter, add_special_tokens=False) != ids + [token]:
            raise ValueError(f"Answer boundary changes tokenization for slot {letter}")
    return ids, slots, digest(prompt)

토큰 예산 초과 시 자르지 않고 에러를 냅니다. 또 답 레터를 붙였을 때 토큰화가 정확히 그 1슬롯만 늘어나는지 확인해 프롬프트/답 경계를 고정합니다.

A.5 — 1회 forward, 마지막 위치 로짓

def _forward(model, inputs):
    params = inspect.signature(model.forward).parameters
    kwargs = dict(inputs, use_cache=False, return_dict=True)
    if "logits_to_keep" in params: kwargs["logits_to_keep"] = 1
    return model(**kwargs).logits[:, -1, :]     # (batch, vocab); 샘플링 없음

모델을 한 번만 돌려 마지막 위치의 다음-토큰 분포만 취합니다. logits_to_keep=1로 전체 시퀀스 로짓 텐서 생성을 피합니다.

A.6 — 슬롯 취합, softmax, 결정

def score(model, tokenizer, row, metadata, max_tokens=4096):
    import torch
    ids, slots, prompt_hash = encode_prompt(tokenizer, row, max_tokens)
    device = next(model.parameters()).device          # 모델을 따라감
    inputs = {"input_ids": torch.tensor([ids], device=device),
              "attention_mask": torch.ones((1, len(ids)), device=device)}
    if device.type == "cuda": torch.cuda.synchronize(device)   # CPU에선 no-op
    with torch.inference_mode():
        vocabulary = _forward(model, inputs)[0].float()        # (vocab,)
    selected = vocabulary[slots].cpu().tolist()   # A, B, C, ... 위치의 로짓
    return {"option_ids":[o["id"] for o in row["options"]],
            "option_logits": selected, "probabilities": softmax(selected), ...}

이것이 "JEV화"의 전부입니다: 표준 AutoModelForCausalLM에게 생성을 시키지 않고, 다음-토큰 로짓을 한 번 물어본 뒤, 옵션 슬롯들의 arg-max가 곧 결정입니다.

A.8 — 하나의 state를 여러 기준에 재사용 (shared 모드)

shared.py는 state를 KV 캐시에 한 번 prefill하고 cache.reorder_cache(...)로 브랜치에 복제한 뒤, 벡터 logits_to_keep로 모든 기준의 답 위치를 한 번의 배치 forward로 평가합니다 — 프리필 1회, 결정 다수. 이 경로도 CUDA에서만 sync합니다.
